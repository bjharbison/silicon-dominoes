The 2026-10-25 audit found that a run gets about 200 web searches across all its agents. So this run took records in queue order until the selected findings came to about 165, which was the first 29 records with 164 selected findings. Each checker was given a fixed search budget. All 164 findings were checked, so every record in that group could be audited completely. This avoids last run's problem of records left half-checked.

## Method

1. **Mechanical.** All 237 records pass `check_country.py`, before and after the corrections. All 237 codes in `queue.json` `done` have a file, and every file is listed in `done`. RUNLOG entries since the last audit (desk passes from 2026-10-25 run 5 through 2026-10-26 run 6) report no guard refusals. They do report two recurring process points:
   - `add_repo` was unavailable, so runs used the existing clone.
   - Many reviewer calls were deferred.
2. **Coding read-through.** One desk-review agent with no web access read all 29 records against `SPEC.md` v0.2. It raised 46 issues: 7 required by SPEC and 39 judgment calls. The patches that AUDIT-2026-10-25 had listed as SPEC-required for these records were applied too.
3. **Source verification.** Nine independent checkers handled eight batches of 14–24 findings, plus one single-finding batch for RUS-010, which one checker had missed. None of them had written the findings. Each fetched only URLs from its own search results and fetched no Chinese-hosted sites. One checker had two fetches blocked (DCD's QGDC page and a 2021 Developing Telecoms page). In total about 170 searches were used.
4. **Corrections**, all under step 4:
   - factual fixes backed by a page a checker read;
   - `still_current` set from checker evidence;
   - notes added with the prefix `Audit 2026-10-28:`;
   - new sources added with `opened: true`;
   - the recoding listed below.

   Corroboration was upgraded only where the audit opened an independent S1–S3 source from a different host that supports the finding, which together with the existing opened sources meets the S1/S2 requirement. Echoes of the same release did not count, and nor did pages that do not name the controller.

## Rule problems — proposals for Brian (not applied)

1. **Run size (repeat).** Brian's cap is 150 records, `AUDIT_PROCEDURE.md` says 80, and the guard allows 120. At the current selection rule and about 200 searches per run, roughly 30 records can be audited fully. *Proposal:* change the procedure's 80 to 150 for scope and read-through, and state that source verification covers records in queue order until the search budget is spent. That is what this run did.
2. **A `not_supported` verdict can promote a country out of "insufficient data".** Setting IRN-003's pole to null removed a negative sanctions reversal, and Iran moved from insufficient to *leans PRC* on 0.95 total weight. *Proposal:* when a reversal is found `not_supported`, also exclude the finding from the total (for example `still_current: false`), or keep the country hatched until reviewed.
3. **Who controls cables.** SPEC treats cables as equipment (vendor = controller), so Google-owned systems become ASN/SubCom (TGO-004, PAN-005). SHN-001 still has Google as controller. *Proposal:* say whether a hyperscaler that owns and operates a private cable is the controller, which the "documented as operating" clause suggests.
4. **Repeats from AUDIT-2026-10-25, still open:** vendor releases as S1 or S4 (2), echoes as independent sources (3), the "single opened S1" exception (4), the pole when the vendor is unknown (5), whether corroboration must cover the vendor (6), default reversal reasons (7; NOR-004 is another case of a security reason coded commercial), model-release tiers (8), and global-layer overlap (9).
5. **Tiny totals produce strong labels.** RUS moved from insufficient to *leans PRC* on 0.85 total weight after a domestic finding was corroborated. *Proposal:* show the total weight next to the cell, or raise the 0.70 threshold.
